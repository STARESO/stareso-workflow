# Guide: a data analysis project in R, the STARESO way

Defaults for analyses that start from field or lab data (spreadsheets, CSV exports, app backups), produce figures and tables, and end in an HTML report. Drawn from the visitor-count analysis of project B and the litter analysis of project D [L]. Everything here is a **default**; the grilling decides what differs for a project.

**Read only the sections you need**: the skills and the slice briefs name section numbers.

---

## 1. Target profile
- One analyst (the maintainer), colleagues who read the report and reuse the figures, sometimes a reviewer.
- Data arrive as versioned files (`v1`, `v2`…) that are never edited by hand after import: every correction is code.
- Outputs are figures (PNG), tables (CSV) and one report (HTML, self-contained); later a Word or PDF export of the same report.
- Reproducible in one command from the raw files, on another computer, in a year.

## 2. Tools
| Layer | Choice | Notes |
|---|---|---|
| Language | **R ≥ 4.4**, run with `Rscript --vanilla` from the project root | RStudio project file for the user; Claude runs scripts, never an interactive session. |
| Packages | `renv` lockfile; `dplyr`, `tidyr`, `stringr`, `lubridate`, `ggplot2`, `scales`, `yaml`, `readr`/`openxlsx`, `testthat`, `lintr`; `vegan`/`FactoMineR` when the plan says so | **Dependency rule:** ask before adding a package and write what it is for (CLAUDE.md "Approved"). |
| Report | **Quarto** `.qmd` → HTML `embed-resources: true` | French text, `lang: fr`, figures loaded from `outputs/`, not recomputed in the report. |
| Config | `config/paths.yml`: the **only** place that names files and folders | Scripts read `paths <- yaml::read_yaml("config/paths.yml")`; no literal path elsewhere. |
| Style | `.lintr` (120 columns, native or magrittr pipe chosen once), `styler` optional | `check` runs lintr on `R/`, `main/`, `tests/`. |

## 3. Folder structure
```
.claude/settings.json      read guard on private/ and data/raw (section 3b)
CLAUDE.md                  rules, Commands table, approved packages
config/
  paths.yml                every input, intermediate and output path, by name
  <topic>.yml              method parameters (thresholds, clustering settings, units)
  <lookups>.csv            small reference tables kept in git (codes, labels, statuses)
data/                      git-ignored (section 3b)
  raw/                     files as received, versioned names, never edited
  processed/               tables written by the pipeline (rds + csv), with a README of columns
R/                         functions only, one file per concern (import, controls, derived tables,
                           figures_<family>, stats_<family>, report helpers); no side effects at source time
main/                      scripts that run in order; each one reads config, sources R/, writes outputs
  01_preprocessing.R  02_<family>.R …  run_all.R
dev/                       exploration scripts, run by hand, never by run_all
tests/
  testthat/                unit tests of R/ functions on toy data
  regression/              snapshot of key outputs (counts, sums, file list) to catch silent changes
  run_tests.R
outputs/                   git-ignored: <family>/<kind>/<name>.png, tables/*.csv, synthese/
report/
  <project>_report.qmd     the report; renders to outputs/report/<project>_report.html
docs/                      PLAN, GLOSSARY, decisions, ROADMAP (+ roadmap/), IDEAS, QUESTIONS, FEEDBACK, BUILD-LOG, LOGBOOK
private/                   sources/locked, sources/readable, INDEX.md, backups (section 3b)
```
Conventions:
- **Code in English** (functions, variables, column names after import), **report, figure labels and comments in French** unless the plan says otherwise; comments short, descriptive ("Vérification des doublons…"), explaining the why.
- Each `main/` script starts with a header comment: title, what it reads, what it writes, how to run it; it runs in its own environment (`run_all.R` sources each in `new.env()`).
- Column names: snake_case, units in the name when ambiguous (`surface_m2`, `densite_1000m2`), dates ISO, decimal point in files, comma only in rendered French text.
- Factor levels and labels defined once in a lookup (`R/labels.R` or a config CSV), reused by every figure.

### 3b. Private material and data
- `data/raw/` and `data/processed/` are git-ignored and treated like `private/data/`: Claude learns their **structure only** (columns, types, counts, ranges, NA rates) through a script the user agreed to run; scripts print counts, never rows. Reference documents go to `private/sources/locked|readable/` as in every stareso project.
- Development and tests use a **toy sample** generated by a script (`dev/make_toy_data.R`, invented values, same columns), stored in `tests/toy/`, committed.
- Real names (observers, people) stay in the data; figures and tables aggregate or anonymise as the plan says.

## 4. Pipeline rules
- **One command rebuilds everything** from `data/raw/`: `Rscript --vanilla main/run_all.R` (the `run` command). It refuses to start outside the project root, runs each step in order, and ends with a count of files written per output folder.
- Steps are **registered** in `config/paths.yml` (`scripts:` list) and read from there by `run_all.R`: a new step is one file plus one line.
- **Controls, not corrections:** import scripts check (row counts against the source, keys unique, values in range, totals conserved between raw and processed) and `stop()` or `warning()` with a message; anomalies are listed in a table in `outputs/tables/controls_*.csv`, never silently fixed. Scientific hypotheses (aggregations, imputations, exclusions) live in `config/*.yml` and are quoted in the report.
- Intermediate tables are written as `.rds` (types kept) and `.csv` (readable), both named in `paths.yml`.
- Every output file name says dataset, subject and kind: `macro_fond_densite_par_zone_barplot.png`.
- No `rm(list = ls())`, no `setwd()`, no absolute paths, no `library()` calls inside `R/` files (only in `main/` and the report).

## 5. Figures
- One theme function in `R/figures_common.R` (`theme_stareso()`), one palette registry (named vectors; sequential scales for densities, categorical for groups, colour-blind safe, red reserved for alerts/limits), saved sizes in one place (`save_png(g, path, width, height)`).
- Each figure function takes a tidy table and returns a `ggplot`; the `main/` script saves it. No data wrangling inside figure functions beyond ordering.
- Facets and panels share scales when values are compared; "n =" and effort shown on the figure when the comparison depends on it.
- A `outputs/figures.csv` registry (file, script, data table, caption) is written by the pipeline and read by the report.
- **A style change covers its whole figure kind.** A change to how figures look (season marks, labels, subtitles, colours, point layers) names the figure kind it applies to (every boxplot, every PCA biplot, every point figure) and lists every figure of that kind from `figures.csv`, so one slice changes them all. Rule from the waste-study project (2026-10-21), where 11 slices reworked the season marks and the PCA figures because each test found figures the previous slice had missed.

## 6. Report (Quarto)
- Header: title, subtitle, author (institution), `date: today`, `lang: fr`, `format: html: embed-resources: true, toc: true`.
- The report **loads** outputs (tables, PNG) and writes the text; it never recomputes. Numbers quoted in the text come from the tables through inline `r` so they cannot drift.
- Sections: context and protocol hypotheses · data and controls (what was received, what was excluded and why, counts) · results per family · synthesis · methods and parameters (from `config/`) · session info.
- **Writing:** report prose and figure texts are written in good scientific French: full, clear sentences, one idea each, linked by connectors (« alors que », « tandis que », « ce qui »), never chained with semicolons. No « ; » in running text. Bullet points only where a list helps (protocol hypotheses, limits), each item a complete sentence. Numbers carry their unit and their sample size, the reading comes before the caveat, and a caveat is stated once in its section rather than repeated in every caption.
- The `render` command produces the HTML; the user opens it (Claude cannot view HTML here; it views the PNG figures with the Read tool and the tables as text).

## 7. Tests and regression
- `tests/testthat/`: every function in `R/` with a non-trivial rule has a test on toy data (conservation of totals, factor levels, date parsing, edge cases).
- `tests/regression/snapshot.csv`: key numbers of the real run (row counts per table, sums of main variables, list of output files). `check` compares the current run with the snapshot and fails on any difference; a slice that changes numbers on purpose updates the snapshot in its commit and says why in its brief.
- `tests/run_tests.R` runs both; `check` = lintr + tests.
- **Speed recipe (set up in M0, not after the first slow build).** An R slice costs mostly R start-up, the pipeline run, lintr on the whole project, the pixel comparison and the render, not the model's work. So: lintr counts are cached per file by md5 (with `.lintr`) and only changed files are linted again; `check --rapide` runs testthat and lintr only, for slices that touch no pipeline code (docs, tests, report wording); a helper runs only the `step` scripts its slice touches, never the whole `run`, then the regression once; a figure-only slice reruns only the figure scripts from the processed tables; builder helpers run at effort `medium`. In the waste-study project this brought the median time per slice from about 7–8 min (M1) to 4–5 min (M5–M7), against about 3 min for a Next.js app.

## 8. Logbook
`docs/LOGBOOK.md`: dated entries (ISO date, `HH:MM` Europe/Paris) of what was decided and found while analysing: data problems and how they were handled, method choices, numbers that surprised. Written by the slices (one line each) and by the user. This is the scientific memory of the project; PLAN holds the decisions, QUESTIONS the open points.

## 9. Commands (what the skills run)
| Name | Command | Notes |
|---|---|---|
| `check` | `Rscript --vanilla tests/run_tests.R` (lintr + testthat + regression; `--rapide`: lintr + testthat only) | `--rapide` on every slice before merge; the full `check` once per milestone and on slices that touch numbers (§10) |
| `run` | `Rscript --vanilla main/run_all.R` | the whole pipeline from raw data; counts only on stdout |
| `step` | `Rscript --vanilla main/<script>.R` | one step while building it |
| `render` | `quarto render report/<project>_report.qmd` | after `run` |
| `structure` | `Rscript --vanilla dev/describe_data.R` | columns, types, counts of the raw files; never rows |

On Windows the R binary may not be on PATH: CLAUDE.md names it (`& "C:\Program Files\R\R-4.x.x\bin\Rscript.exe"`).

## 10. Verification (what "done" means here)
**Checks are rare: the user is the check for how things look.** Automatic checks guard the numbers, not the details of a figure. Waiting on gates for small visual points cost most of the waiting time in the waste-study project (2026-10-21), so:
- **Looks go through a tune pass** with the user (`stareso-test`, [look] points), never through a slice, a helper or a checker.
- Per slice: `check --rapide` (testthat + cached lintr); `step` of the touched script runs clean with counts printed; new figures opened by the helper (Read on the PNG) and described in one line ("verified: 12 bars, legend ordered, no overlapping labels"). The CSV regression runs only when the slice touches the processed tables, a statistic or a config hypothesis. The PNG regression runs only for a pure refactor (figures must stay identical); a slice that changes figures on purpose skips it and retakes the PNG baselines.
- Per milestone: the full `check` once at the end. The `stareso-slice-checker` helper runs only when the milestone changes numbers or methods, or when the user asks: it then runs `run` from scratch, compares the regression snapshot, opens the new or changed figures and reports a table `figure · ok / problem`. Otherwise the user's test is the check. `render` must succeed. For a style change, every figure of the kind the brief names is opened (a contact sheet, not a sample).
- Per test round ("test time"): the user reads the rendered report and the figures in the browser, and talks; feedback is logged as in every stareso project.

## 11. Default roadmap (adapt in setup)
Slices are vertical: a slice goes from data to an output someone can look at. Never "all imports, then all figures".

**M0. Scaffold:** renv + lockfile · `config/paths.yml` with the raw files · `run_all.R` skeleton · `.lintr`, `tests/run_tests.R` with the lint cache and `--rapide` (§7 speed recipe), toy data · `describe_data.R` run by the user, structure recorded in `docs/PLAN.md` §4 · LOGBOOK.
**M1. Import and controls:** one slice per raw table: import, column renaming from the lookup, controls table, processed rds/csv, README of columns, regression snapshot.
**M2. Derived tables:** effort, densities, derived classes; each with conservation checks and a test.
**M3. Figures per family:** one slice per figure family (coverage, top-N, densities by zone, composition…), theme and palette first.
**M4. Statistics / models:** one slice per method (bootstrap CI, paired tests, ordination, clustering, GLM), each with a toy-data test and a parameter block in `config/`.
**M5. Report:** one slice per section, numbers through inline code, figures registry.
**Tidy slice at the end of every milestone** (`M<n>.tidy`): shared code into `R/`, dead code out of `main/`, exploration moved to `dev/`, snapshot and README of columns updated.
**H. Waiting on human input:** reviewer comments, new data version (a version bump is a slice: path in `paths.yml`, controls rerun, snapshot updated, LOGBOOK line).

## 12. Slice brief shape (pack-specific lines)
- Files: `R/<module>.R` to extend (never a copy), `main/<step>.R`, `config/…`, `tests/testthat/test-<module>.R`.
- Done when: `check --rapide` passes (the full `check` when the slice touches numbers, §10), `step` prints the expected counts, the output files exist with the names from `paths.yml`, the figure was opened and described, the LOGBOOK line is written.
- Style change: a `Figures:` line names the figure kind and lists every figure of that kind (from `figures.csv`); done when each listed figure was opened and shows the change.
- Risk: `opus` for a slice that chooses a statistical method or reinterprets a protocol hypothesis; `haiku` for labels, palettes, report wording.
