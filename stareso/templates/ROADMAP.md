# <ProjectName>: roadmap

Written by stareso-setup from docs/PLAN.md. One slice = one small vertical change that leaves something
usable (a screen, a figure, a table). Each brief is self-contained: a fresh helper works from it alone.

**Layout.** One file per milestone in `docs/roadmap/` (`M1.md`, `M2.md`, `H.md`, `P.md`). The build ticks the boxes
(`slice-done` tool), test markers show what has been tested, and the table below is regenerated by the tools: edit the
milestone files, never the table.

**Numbering.** Milestones `M1`, `M2`, … in build order; a slice is `M<milestone>.<n>`. Lettered milestones never
renumber: `H` = waiting on human input (always last before delivery), `P` = after the first delivery. New fix or
feature milestones take the next free number and go before `H`. A slice id never changes once given.

**Slice format** (in the milestone files):

```
- [ ] **M3.2 · Title** · model: sonnet | haiku | opus · after: M3.1 · check: now (optional) · [human] (optional)
  - Goal: what works afterwards, in one sentence.
  - Files: the module to extend or create (one feature = one module; never a copy), the files touched.
  - Steps: 2 to 5 short lines.
  - Done when: observable result + `check` passes (+ the pack's verification when there is an output to look at).
  - Guide: pack guide sections to read (e.g. §6, §8).
```
`after:` names the slices that must be merged first (shared files or data). A slice without `after:` whose Files
overlap no other open slice can run in parallel (fast profile). `model: opus` only for a real risk (security, legal
records, migrations on real data, a statistical method); `check: now` asks the checker helper right after the slice;
`[human]` marks a slice needing the user (secrets, accounts, online database, a real data file).
