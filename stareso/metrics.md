# Workflow metrics

The single definition of the numbers a retro reports. Each metric is defined once here, and the retro skill points to this file instead of keeping its own table.

**Source** says where the number comes from. "records" means the project's own files (the build records `docs/data/builds.jsonl`, `docs/QUESTIONS.md`, `docs/FEEDBACK.md`, the roadmap and git), which any harness can read. "usage" means the session transcripts, read by `session-stats` into `docs/data/sessions.jsonl`. Only `session-stats` knows the transcript format of a harness, so a port to another harness replaces that one reader and keeps the definitions.

**Tool** names what computes the number. A retro copies tool numbers and does not recompute them. When no tool gives a number yet, the retro counts it from the records and says so. When the records cannot give it, the retro writes "n/a".

"≈ equiv" in the table is Claude Code's summary unit (`harness/claude-code/capabilities.md`, usage reader), and its references are Claude Code numbers. Another harness reports its own summary unit, or none, under the token rules below.

## Token metrics

Token metrics stay in tokens, per harness, with no money and no price table. The harness's usage reader (`capabilities/usage.md`) reports tokens by kind (input, cache read, cache write, output) and by model or tier, as the harness logs them. A kind that a platform does not log is "n/a".

Two rules hold everywhere:
- **Never add raw tokens of different kinds**, because a cache read and an output token differ in cost by about 50 times.
- **Never add tokens across models.**

Comparisons are made only within one harness and one tier, per slice. A harness may define one summary unit that weights its own token kinds, and it must say so in its `capabilities.md`. On a subscription, usage limits are spent rather than dollars, which is why the workflow uses no price weighting.

## The usage report (`tools/usage-report.mjs`)

Where the tokens of a project went, from the records only (`docs/data/sessions.jsonl`, `docs/data/builds.jsonl`, the roadmap, git), never from transcripts or code. It has no step of its own: the panel's Usage tab shows it live, the retro reads it, and any session answers a usage question from the commands and the reading guide below. Numbers are copied from the tool, never recomputed by hand.

- `node tools/session-stats.mjs --log` first, from inside the project, refreshes `docs/data/sessions.jsonl`.
- `node tools/usage-report.mjs` prints six tables: step types, sessions, milestones (the 30 most recent, `--all` for every one), steps that merged slices, efficiency by tier, planning rounds. Share % is the first column. Work done before the workflow started (before the first init or retrofit) shows as "—" and stays out of the shares. Sessions are named by number and date, never by their step.
- `--json` gives the same numbers as one compact line, `--charts` the series of the charts, `--builds` the build records with their notes, `--projects` the cross-project index of this machine, `--summary` one line.
- To keep a report, `node tools/usage-report.mjs --all > docs/reports/usage-yyyy-mm-dd.md` writes the tables as a dated Markdown file in the project.
- **≈ equiv** is one number per session that weighs the token kinds by their relative cost (cache read × 0.1, cache write × 1.25, output × 5). The weights are frozen, and it is not money.
- A good reading takes three to five lines: the biggest cost of the period and its cause in the records, how chat-built slices compare with launched builds (≈ equiv per slice), and which tier gives the most change per token, compared with the previous retro entry when there is one.

### How the numbers are built
- **≈ equiv per slice** of a milestone: for a slice whose helper was measured (slice-done reads the helper's own transcript, since 2026-10-22), that helper's ≈ equiv plus an even share of the rest of the merging step (the conductor, the helpers nobody measured); otherwise the ≈ equiv of the step that merged it (session and helpers together) ÷ the slices that step merged. The slices of a step always add up to the step, so a slice built in a chat and one built by a launched build compare directly. "Measured" says how many merges had a logged step.
- **Efficiency by tier:** helper tokens from the build records (the figure a helper reports, its final context, not what it consumed: "Measured" and "Median measured ≈ equiv" give what the measured helpers consumed), lines changed by the slice's merge commit outside `docs/` (kept in the build record when slice-done merged it). Tokens per 100 lines is the median per tier, and a slice above twice its tier's median token count is an outlier. Tiers are chosen by difficulty, so compare a slice with its own tier, not across tiers.
- **Planning rounds** are named `Test n` / `Improve n` in date order, with their session number and the share of their cost spent re-reading older context (Carried).

### The nine charts (what each one shows, how to read it)
Four tiles come first: the workflow cost (≈ equiv since the first init or retrofit), the cost before the workflow (shown, never in a share), the slices built, and the last launched build's cost per slice.

1. **Share of the workflow cost by step type** (horizontal bars). One bar per step type (build, test, improve, manager, chat, retro), as a percentage of the workflow cost. Reading: where the tokens go. Build is expected to lead; a large "chat" bar means work done outside the steps, and a large "manager" bar a manager session kept open across milestones. The tooltip gives ≈ equiv, active hours, turns and the median Carried.
2. **Cumulative cost by step type over time** (stepped lines, log scale, x axis in dates). Each line is the running total of one step type; a vertical jump is one step's whole cost, placed at the step's start. The log scale keeps the small types readable beside build. Reading: when each type started costing and which steps made the jumps (a chat line that climbs steeply is a chat that built or tested). Variant: stacked areas on a linear scale show the composition of the total instead of the timing.
3. **Cost per slice by milestone** (bars coloured by "built by": launched build, in chat, mixed; a dashed reference line at project A M5, 335k). The value is the cost of the step that merged the slices (session and helpers together) divided by the slices it merged, so chat-built and helper-built milestones compare directly. A milestone with no cost per slice yet (nothing merged, or the session that built it left no transcript) is left out of the chart. Reading: launched builds should sit near the reference, chat-built milestones sit far above it; a milestone whose slices were merged during a test carries that test's cost too, which is a limit of the measure, not a cost of the slices.
4. **Context per turn by session** (line; point size = turns; red = over 300 turns). Context per turn = the session's cache read ÷ its turns: the mean of what each turn re-read from the cache (every assistant turn reports it), not the context size at the end, and a little under the true context since fresh input and cache writes are not in it. Reading: it grows with the length of a session and with what the session carried from earlier steps; launched sessions sit near the base (about 100k), long mixed sessions climb past 200k. A red point is a session that should have been split.
5. **Helper tokens against lines changed, one point per slice** (scatter, log scales, colour and shape = tier; crosses = tier medians; grey diagonals = constant tokens per 100 lines; red ring = outlier, over twice its tier's median tokens). Reading: each tier forms its own cloud (light bottom left, strong top right), because tiers are chosen by difficulty: compare a point with its own cloud, never across tiers. A point far above its cloud cost more than its size justifies (look at its note with `usage-report.mjs --builds`); a point far below is a cheap large change. The diagonals let the eye read tokens per line; the medians per tier are the table's "tokens per 100 lines".

6. **Conductor against helpers, per step that merged slices** (stacked horizontal bars: the session's own cost and its helpers' cost in ≈ equiv; the label gives the slices merged). The conductor share is the "conductor vs helpers" metric above (target: conductor under 50 % of a build). Reading: a launched build should be mostly helpers; a bar that is all conductor is a chat or a test that built or merged itself; a build with a large conductor part spent its turns on checks, rebuilds or fixes rather than delegating. Helper cost is the helpers' own ≈ equiv, cache writes included (before the datasets it left the cache writes out, so older reports show a larger conductor share).

7. **ETA against what happened, per merged slice** (a dumbbell per slice: ○ = minutes predicted, ● = minutes it took, joined by a line in green when within 25 %, amber when late by more, blue when early by more). When a helper is first seen running (by status or the panel), `progress-graph.mjs` keeps its predicted merge time in this machine's `stareso/data/eta/<project>.jsonl`, never in the project. Once the slice merges, actual ÷ predicted is one sample, and the median of the last 20 (at least 4) becomes the factor that scales the time of one slice in every later ETA (clamped to 0.5–3, and measured against the raw estimate so it never compounds). Reading: short green dumbbells mean the ETAs hold, and ● right of ○ is a slice that took longer than predicted; a factor far from 1 means the merge gaps alone mislead (a checker, rebuilds, usage pauses).
8. **Gates inside the builds** (stacked bars, one per gate: passed runs, then failed ones; value: runs and failed %). The caption gives the checking cost and its share of the build cost, the runs per built slice and the flakes ("Failing" in the table above). Reading: a gate that fails often is either catching real breakage or flaky, and the flakes say which.
9. **Plan interventions, per milestone** (stacked bars: slices built as planned, then off plan; value: off plan out of built, and their cost). The caption gives the off-plan share of the build cost and the manager messages that steered the plan ("Plan interventions" in the table above). Reading: a long amber bar is a milestone redesigned while it was built.

A session marked "(transcript gone)" (`session-stats --print`) was logged, then its transcript was deleted (archiving or clearing a session in the app deletes it): its numbers come from `docs/data/sessions.jsonl`, to which `session-stats --log` appends every session that changed, so a session logged once never drops out of the record again. A session that any live read saw (the status panel, `usage-report --live`) is kept in the per-machine cache when its transcript goes, and the next `--log` saves it. One that no live read nor `--log` ever saw can be brought back from an older USAGE.md in git with `node tools/usage-seed.mjs <git-rev> <session-number>` (its entry says "seeded"); the report's "helper-built slices have no ≈ equiv per slice" line tells when that is worth doing. A slice the build records say a helper built (`docs/data/builds.jsonl`) is charged to a build step only: with none in the records it is unlogged, never charged to a test or chat step that was open at the time.

Costs are ≈ equiv unless the chart says tokens (helper tokens come from the build records and are plain token counts).

## Evaluating a capability on a platform

Each harness lists its capabilities in `harness/<harness>/capabilities.md` with a status (`capabilities/README.md`). A **proposed** row is evaluated once, after one milestone of at least five slices built on that harness, or after the canary for the read guard. The retro of that milestone reads the row, computes the numbers below, writes them in the row's Evidence and sets the status to **adopted** or **rejected**, with a CHANGELOG line. That is one workflow change, so it counts towards the retro's three.

Since 2026-10-20 every build line (a build event since 2026-10-22) carries `harness · helper mode · tier` (`slice-done`, defaults from the `Harness:` and `Helpers:` lines of the project instructions, else `claude-code · subagent`, and the brief's tier). Older lines count as `claude-code · subagent` with the tier of their model. The retro splits the records metrics by harness × helper mode × tier:

| Metric | Definition | Source |
|---|---|---|
| Fix rounds | share of slices whose result is "ok after n fix" or that failed | records (builds) |
| Check-fix slices | `Check fix:` slices added per milestone | records (roadmap) |
| Reworks | as in the table above | records (roadmap) |
| Conductor-built slices | as in the table above | records (builds) |
| Minutes per slice | median gap between consecutive build times within one build run | records (builds) |
| Guard verified | the `Guard:` line under `Pack:` in `docs/PLAN.md` (verified, not enforced, or missing) | records (PLAN) |

Usage metrics (conductor turns and ≈ equiv per slice, Carried, planning cost) are split the same way only where the harness has a usage reader (`capabilities/usage.md`); elsewhere they are "n/a". A row is adopted when its numbers meet the targets of the table above, or stay within the Claude Code references where a target is missing. A cheaper tier or helper mode is adopted for a kind of slice only when fix rounds and check-fix slices do not rise.

## No regression after the harness split

On 2026-10-20 the steps and roles moved into a harness-neutral core, and the Claude Code files became generated (`tools/harness-build.mjs`). Nine generated files came out identical and four grew by less than about 5 %, so nothing should cost more. The next Claude Code build after the split checks it: its conductor turns per merged slice and ≈ equiv per slice are compared with project A M5 (8.8 turns, 335k, 2026-10-20) and project C M28 (19.7 turns, 990k, 6 slices, 2026-10-20), each project against its own reference. A move of more than 10 % in either number means the generated files are inspected first (`harness-build.mjs --check`, then `git diff 54eb59b -- skills agents`), before any other cause is looked for.
