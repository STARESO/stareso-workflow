# stareso-test

**Session:** standard tier · **new session** (the build context is not needed: the roadmap markers say what is new) · normal mode. If this session runs another model, say so in one line.

**Started by a manager:** when the first message is a manager session's launch naming this step (status §5), run it as if the user had typed it. From then on the user talks to this session directly, and the last line says `STEP DONE: test · next: <the next step>` for the manager.

**Heavy session:** if another step already ran in this session (its context is past about 100k tokens: a build, a test, a long chat) and this skill's Session line does not name that step as fine, say in one line before anything else that starting here re-reads that context at every turn (USAGE "Carried", target < 20 %) and ask: continue here or open a new session. Only once per step.

Talk in English unless the user switches to French. Mark the switch: chapter "Test" if available, first line **"— Test time —"**.

## 1. Prepare
1. Read `AGENTS.md` (pack, Commands), `docs/ROADMAP.md` (overview). In each milestone file of `docs/roadmap/`, the slices ticked after the last `<!-- test: … -->` marker are what is new.
2. `app-next`: never rebuild the dev database with the bare reset: `rebuild` only, dev server stopped. Start the dev server with the preview tool and open the app in the browser pane; the dev accounts are in the project files (never type a real code). `analysis-r`: run `run` then `render`; tell the user where the HTML is (they open it); open the new figures yourself with the file-reading tool when a point needs it. `godot-game`: run `check`, then `build` the tablet build when PLAN targets tablets and say where it is; the user plays (never open a game window yourself: a `shot` through the wrapper when a point needs a picture). The checklist is the lines of `docs/PLAYTEST.md` added since the last test, each with where to tweak it.
3. Give the user a short checklist: for each new screen, behaviour, figure or report section, where to go and what should happen (one line each, from the slices' "done when"). Mention the size and theme controls (phone width, dark / light) if layout changed.

## 2. Collect feedback
- The user clicks around (or reads) and talks, text or voice. Read voice input for meaning.
- When they point at something, use the page tools to find the element and reproduce it; read console errors. Fix nothing yet, except an obvious one-line fix the user asks for right away.
- **Log only, do not plan yet.** Append each point to `docs/FEEDBACK.md` under `## Test yyyy-mm-dd (slices M19.1–M19.4)` as one short line in the user's words, tagged **[bug]**, **[change]**, **[idea]**, **[tune]** (a value to change: game feel, difficulty, timing), **[look]** (`analysis-r`: how a figure or the report looks, changed at once in a tune pass, see below, and logged with "tuned") or **[decision to confirm]** (a point that contradicts `AGENTS.md` or PLAN.md: quote the rule at once). Screenshots: note what they show. Do not write slices or edit the roadmap, PLAN.md or IDEAS.md during the test.
- Restate each point in one line so the user can correct you.
- **Tune pass (`analysis-r`).** A point about how a figure or the report looks (colours, symbols, labels, subtitles, layout, wording of a caption), tagged **[look]**, is not logged for a later slice: change it now, live, with the user as the check. Edit the figure code, redraw only the figures concerned from the processed tables (one `step` or a figure-only call, never `run`), open the PNG with the file-reading tool, show it in one line, and let the user say ok or again; `render` only when the user wants to see it in the report. No helper, no checker, no `check` between tries. A [look] point applies to its whole figure kind (pack guide §5). At the end of the pass, or before a point that is not [look]: one commit, `check --rapide`, the CSV regression only (figures are meant to change), the PNG baselines retaken once, and one BUILD-LOG line `- yyyy-mm-dd HH:mm · tune pass · <n> looks · <figure kinds> · in session`. A [look] point that turns out to change numbers, code shared with the pipeline or a decision stops being one: log it as [change] and it becomes a slice.

## 3. End ("end test", "done testing")
1. **Segment the log into slices.** Read the whole block: drop points superseded later in the same test; group points by screen, module or figure family so that points touching the same files become **one** slice (small: 1 to 5 files; split a bigger group); `after:` between slices sharing files. Ask the user **one** question listing every unclear point, each with your recommended reading; do not guess. Then write the slices in a new milestone file `docs/roadmap/M<next>.md` ("Fixes after the Nth test", usual brief format, module ownership, a bug slice says how to reproduce, a tidy slice at the end), **ideas** as 💭 lines in `docs/IDEAS.md`, **[tune]** points grouped into one tune slice (light tier), or listed in the summary as "tweak yourself: file > property" when the user prefers, and for every **decision to confirm** a slice marked "waits on /stareso-improve" (AGENTS.md and PLAN.md are not edited without the user's confirmation).
2. Summary: bugs, changes, ideas, decisions to confirm, looks tuned in the session, slices created (which points each covers).
3. Records: add `<!-- test: yyyy-mm-dd, up to slice M19.3 -->` after the last tested slice in each milestone file concerned; move every FEEDBACK block beyond the newest two to `docs/FEEDBACK-DONE.md`; (godot-game) move the tried lines of `docs/PLAYTEST.md` to `docs/PLAYTEST-DONE.md`; a point the user decided during the test that answers an open line of `docs/QUESTIONS.md` is ticked there with `**Answer (date): …**`, and a point that needs a decision nobody could take today becomes a new `(test yyyy-mm-dd)` line; run `node <stareso>/tools/roadmap-overview.mjs`, `node <stareso>/tools/session-stats.mjs --log` (refreshes `docs/USAGE.md`) and `node <stareso>/tools/docs-check.mjs` and fix what it flags (search the old wording across `docs/` and `AGENTS.md` for any rule or term that changed; if two docs disagree and the right version is unclear, ask). Commit docs.
4. Next step: a decision to confirm or a rule change → `/stareso-improve` first (strong tier, new session) so AGENTS.md, PLAN.md and the briefs agree before building; otherwise offer to build the fix milestone now: `/stareso-build M<next>` (standard tier, new session, auto mode, eco), and to test again after it.
